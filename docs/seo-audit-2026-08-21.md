# Auditoría SEO técnico, local y performance — 2026-08-21

## Alcance

Rama: `feature/seo-tecnico-local-performance`

Objetivo: mejorar indexación orgánica, metadata, semántica, rastreo, datos estructurados, medición de WhatsApp y base de Core Web Vitals sin modificar la lógica comercial del catálogo.

## 1. SEO técnico

### Estado encontrado

- El proyecto usa App Router y Metadata API de Next.js.
- Existían `app/robots.ts` y `app/sitemap.ts`.
- El layout global definía canonical `/`, con riesgo de que rutas sin canonical específica heredaran la Home.
- El layout envolvía todo en `<main>` y las páginas también usaban `<main>`, generando semántica duplicada.
- El carrusel podía renderizar varios `<h1>` porque cada slide con título usaba `<h1>`.
- Los productos ya cuentan con `generateMetadata()` y JSON-LD `Product`.

### Cambios aplicados

- Metadata global reforzada con foco en:
  - Césped Esmeralda.
  - Pasto Kavaju.
  - Limpio.
  - Asunción y Gran Asunción.
- Canonical global `/` eliminado del layout; Home y Catálogo definen canonical específica.
- `<main>` global eliminado del layout.
- Carrusel ajustado para que solo el primer slide sea `<h1>` y el resto use `<h2>`.
- `robots.ts` mantiene indexación pública y bloquea `/api/`, `/admin/`, `/cart` y `/proximamente`.
- `sitemap.ts` mantiene Home, Catálogo, Trabajos y productos públicos; se retiraron filtros de categoría por query string para no enviar URLs no canónicas.

## 2. Core Web Vitals

### Imágenes

- `ProductCard` usa `next/image`, `sizes` responsivo y no usa `priority`.
- Los banners de categoría usan `next/image` y no fuerzan `priority`.
- El hero usa `next/image` y prioriza únicamente el primer slide.
- El hero actualmente renderiza variantes desktop y mobile del primer slide; esto debe medirse en Vercel Speed Insights/Lighthouse porque puede generar más de una precarga candidata para LCP según viewport.

### Renderizado y caché

- La Home está configurada con `dynamic = "force-dynamic"` y `revalidate = 0`.
- La Home consulta Supabase mediante `createClient()` y ese cliente usa `cookies()` de `next/headers`.
- Por seguridad no se cambió a SSG/ISR en esta rama: primero conviene separar las lecturas públicas de catálogo/contenido a un cliente Supabase sin dependencia de cookies y luego aplicar `revalidate`/caché por ruta.

### Próxima optimización recomendada

1. Crear una capa de lectura pública cacheable para Home/Catálogo.
2. Migrar datos públicos a `unstable_cache`/`revalidate` o equivalente compatible con la versión actual de Next.js.
3. Medir LCP real de Home en Preview y confirmar qué variante del hero es el elemento LCP.
4. Revisar peso real de banners y fotos en Speed Insights antes de reducir `quality` de forma general.

## 4. Google Ads, Google Tag y Analytics

### Estado encontrado

- GA4: `G-X4SL2XNW02` estaba implementado.
- Google Ads: `AW-18381728232` estaba configurado en `gtag`.
- Google Tag `GT-MKR6HCPJ` no estaba cargado explícitamente.
- Los clics de WhatsApp ya disparaban `whatsapp_click` y guardaban atribución `gclid`, `gbraid`, `wbraid` y UTM.
- La conversión directa de Google Ads no podía dispararse porque `GOOGLE_ADS_CONVERSION_LABEL` estaba vacío.

### Cambios aplicados

- Se carga `GT-MKR6HCPJ` como Google Tag principal.
- Se mantienen configurados GA4 y Google Ads.
- `GT-MKR6HCPJ` se configura con `send_page_view: false` para evitar duplicar el page view que envía GA4.
- El evento `whatsapp_click` continúa enviando contexto de página, producto, servicio y campaña.
- Se agregó soporte para `NEXT_PUBLIC_GOOGLE_ADS_WHATSAPP_CONVERSION_LABEL`.
- Si el label está configurado en Vercel, cada clic válido de WhatsApp dispara también el evento `conversion` a `AW-18381728232/<label>`.

### Pendiente externo

Para habilitar la conversión directa de Google Ads hace falta copiar el Conversion Label real de la acción de conversión “WhatsApp” de Google Ads y cargarlo en Vercel como:

`NEXT_PUBLIC_GOOGLE_ADS_WHATSAPP_CONVERSION_LABEL`

No se inventó ningún label.
